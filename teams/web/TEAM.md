# پروتکل همکاری تیم (Team Protocol)

این فایل قانون کار گروهی ۵ ایجنت است. هر بار که پروژه‌ای شروع می‌شود، این جریان اجرا می‌شود.

---

## ۱) جریان کار (Pipeline)

```
۰. INTAKE      رهبر تیم: گرفتن بریف، شفاف‌سازی ابهام‌ها، تعیین محدودیت‌ها
۱. DISCOVERY   UX : پرسونا، اهداف کسب‌وکار، تحلیل رقبا، KPI موفقیت
۲. STRUCTURE   UX : نقشه سایت، جریان کاربر، وایرفریم متنی، معماری اطلاعات
۳. DESIGN      UI : توکن‌های طراحی، پالت، تایپوگرافی، کامپوننت‌ها، حالت‌ها، ریسپانسیو
۴. BUILD-FE    FE : ساختار فایل، HTML سمانتیک، CSS، JS، انیمیشن، بهینه‌سازی
۵. BUILD-BE    BE : مدل داده، API/صفحات PHP، احراز هویت، امنیت، یکپارچه‌سازی
۶. VERIFY      QA : تست، ممیزی کارایی/دسترس‌پذیری/امنیت، کراس‌براوزر، اصلاح
۷. SHIP        رهبر تیم + QA: راهنمای دیپلوی، چک‌لیست راه‌اندازی، نگهداری
```

مرحله‌های ۴ و ۵ می‌توانند موازی پیش بروند، به‌شرطی که **قرارداد داده (Data Contract)** در مرحله ۳ امضا شده باشد.

---

## ۲) قرارداد داده (Data Contract) — پل بین FE و BE

قبل از نوشتن کد، UI و BE این جدول را پر می‌کنند و FE بر اساس آن کد می‌زند:

```
ENDPOINT   : POST /api/appointment
REQUEST    : { name: string, phone: string(11), service_id: int, date: 'YYYY-MM-DD', time: 'HH:MM' }
RESPONSE   : 200 { ok: true, ref: 'APT-8F3K' }
ERRORS     : 422 { ok: false, field: 'phone', message: 'شماره معتبر نیست' }
           : 429 { ok: false, message: 'تعداد درخواست زیاد است' }
SECURITY   : CSRF token در هدر X-CSRF-Token | Rate limit: 5/min/IP
```

**قاعده:** هیچ فیلدی که در قرارداد نیست، در کد ظاهر نمی‌شود. تغییر قرارداد = اطلاع به هر دو طرف.

---

## ۳) قالب تحویل بین ایجنت‌ها (Handoff)

هر ایجنت خروجی‌اش را با این سربرگ می‌دهد:

```
👤 [کد] نام ایجنت — مرحله N
─────────────────────────────
📌 خروجی: چه چیزی ساخته شد
📥 ورودی گرفته‌شده از: کدام ایجنت / کدام تصمیم
⚠️ ریسک‌ها و فرض‌ها: چه چیزی حدس زده شد و باید تأیید شود
➡️ تحویل به: چه کسی، برای چه کاری
```

---

## ۴) جدول مسیریابی (چه کاری به چه کسی)

| درخواست کاربر | مسئول اصلی | پشتیبان |
|---|---|---|
| «سایت برای چه کسانی و با چه ساختاری؟» | UX | UI |
| نقشه سایت، منو، دسته‌بندی محتوا | UX | BE |
| رنگ، فونت، لوگو، استایل بصری | UI | UX |
| طراحی کامپوننت و حالت‌ها (hover/focus/error) | UI | FE |
| کد HTML/CSS، انیمیشن، ریسپانسیو | FE | UI |
| JavaScript، فرم تعاملی، AJAX، فریم‌ورک | FE | BE |
| PHP، Laravel، دیتابیس، پنل ادمین، API | BE | QA |
| امنیت، لاگین، پرداخت، ایمیل | BE | QA |
| سرعت سایت، Core Web Vitals | FE | QA |
| تست، باگ، ممیزی، کراس‌براوزر | QA | همه |
| هاست، دیپلوی، DNS، SSL | BE | QA |
| سئو تکنیکال | FE | UX |
| متن‌نویسی و لحن محتوا (UX Writing) | UX | UI |

## ۴-ب) مسیریابی گسترده — قابلیت‌های on-demand

این چهار مورد ایجنت جدید **نیستند**؛ همان ۵ عضو با چک‌لیست اجباری مخصوص آن درخواست.

| اگر کاربر بگوید | چه کسی اجرا می‌کند | از کدام بخش استفاده می‌کند |
|---|---|---|
| «سئو و محتوایش را هم بنویس» | رهبر تیم + `UX` (کلیدواژه و محتوا) + `FE` (تکنیکال) | `UX` §هـ استراتژی محتوا و سئو + `FE` §SEO تکنیکال |
| «امنیتش را جدی بررسی کن» | `BE` (رفع) + `QA` (ممیزی) | `QA` §ممیزی عمیق OWASP Top 10 |
| «درگاه پرداخت ایرانی می‌خوام» | `BE` (یکپارچه‌سازی) + `QA` (تست) | `BE` §درگاه پرداخت ایرانی + `QA` §تست درگاه پرداخت |
| «راهنمای دیپلوی بده» | `BE` (سرور/SSL/بک‌آپ) + `QA` (چک‌لیست راه‌اندازی) | `BE` §Deploy & Ops + `QA` §چک‌لیست نهایی راه‌اندازی + §تحویل: مستند فنی |

**قاعده:** وقتی یکی از این جمله‌های کلیدی آمد، بخش مربوطه **اجباری** می‌شود و خروجی بدون آن ناقص است.

---

## ۵) تعریف «تمام‌شده» (Definition of Done)

یک کار وقتی تمام است که **همه‌ی** این‌ها درست باشند:

**UX**
- [ ] هر صفحه هدف مشخص و یک CTA اصلی دارد
- [ ] مسیر کاربر بدون بن‌بست است (خطا → راه‌حل)
- [ ] متن‌ها فارسیِ روان و بدون ترجمه‌ی ماشینی‌نما

**UI**
- [ ] همه‌ی رنگ‌ها از توکن‌های سیستم طراحی می‌آیند (بدون hex پراکنده)
- [ ] کنتراست متن ≥ 4.5:1 (متن بزرگ ≥ 3:1)
- [ ] هر کامپوننت حالت‌های default / hover / focus / active / disabled / error / loading را دارد
- [ ] در ۳۶۰px، ۷۶۸px و ۱۴۴۰px درست نمایش داده می‌شود

**FE**
- [ ] HTML معتبر و سمانتیک (یک `<h1>`، سلسله‌مراتب درست عنوان‌ها، `alt` روی تصاویر)
- [ ] CSS با واحدهای منطقی و properties منطقی (`padding-inline`) — RTL-safe
- [ ] بدون خطای کنسول؛ JS بدون وابستگی غیرضروری
- [ ] Lighthouse Performance ≥ 90، Accessibility ≥ 95
- [ ] کار با کیبورد و فوکوس قابل مشاهده

**BE**
- [ ] همه‌ی کوئری‌ها با prepared statement
- [ ] اعتبارسنجی سمت سرور برای همه‌ی ورودی‌ها
- [ ] محافظت CSRF روی همه‌ی فرم‌های POST
- [ ] رمز عبور با `password_hash()` و `password_verify()`
- [ ] هدرهای امنیتی + `display_errors = Off` در محیط production
- [ ] ساختار دیتابیس با کلید خارجی و ایندکس مناسب

**QA**
- [ ] تمام سناریوهای جریان اصلی تست شده (خروجی واقعی، نه «باید کار کند»)
- [ ] تست در Chrome/Firefox/Safari و موبایل
- [ ] مسیر خطاها تست شده (ورودی خالی، طولانی، مخرب)
- [ ] گزارش: چه چیزی تست شد، چه چیزی تست نشد و چرا

---

## ۶) قوانین حل اختلاف

1. اگر FE و BE بر سر شکل داده اختلاف داشتند → **قرارداد داده** رأی نهایی است.
2. اگر UI و UX بر سر چیدمان اختلاف داشتند → **هدف کاربر** رأی نهایی است (نه سلیقه).
3. اگر سرعت و زیبایی در تضاد بودند → **سرعت**، مگر اینکه برند صراحتاً چیز دیگری بخواهد.
4. در همه‌ی موارد، رهبر تیم تصمیم نهایی را با ذکر دلیل می‌نویسد.
